# 权限维度必须同构存在于每一条跨请求共享路径（租户 × 密级 × 信任域）

状态：accepted（2026-09-11，第四轮 QA 红队 P0 教训升格）

上下文：系统宣称"tenant + auth_level 双维引擎层硬过滤"，ES/Qdrant/L1/L2/SOP 五处实现均正确。
但第四轮三 Persona 测评实证了两处破防：
① Single-Flight 组键 `fingerprint+authLevel` 缺 tenant——告警风暴（核心卖点场景）下，
   跨租户同密级并发 follower 直接回放 leader 全文+引用；串行路径完全正确，竞态路径破防。
② admin 门禁只认 `auth_level>=3`——把"密级"当"信任"，外来租户 L3 可重建共享索引、
   清空全局缓存（测评中被真实误触发，blue/green 设计救回数据）。
根因同构：设计语言里"权限"被默认等同于"密级"，而租户与信任域（role）在共享路径上被系统性遗漏。

决策：
1. **权限三元组完备性**：任何跨请求共享状态（缓存 key、向量过滤、去重键、Single-Flight 组键、
   运维面授权）必须同构携带 `tenant × authLevel × role` 中与其语义相关的全部维度；
   新增共享路径时以"逐条枚举"为验收项（A2-9 并发用例 + AdminControllerTest 18 格矩阵为回归锁）。
2. **密级 ≠ 信任域**：`auth_level` 只约束"能看到多密的文档"；平台级资源（索引/集合/全局缓存/
   账号库备份）的写权由 DB `role=="platform"` 单独判定（保持 ADR-0005"DB 是唯一真相"，
   不引入配置双源）。customer 高密级用户默认无平台权。
3. **绊线纵深**：共享载荷携带 `src_tenant`，回放入口 fail-closed 比对请求者租户——
   主闸门失守时宁可误伤（error 收尾）不泄露；审计行使"请求租户≠内容租户"成为可 grep 告警面。

理由：租户隔离的难度不在"过滤条件写对"，而在"每一条旁路都写对"——并发共享、缓存回放、
运维面都是过滤器管不到的旁路，必须逐一枚举、逐一上锁、逐一留痕。

后果：
- 正面：跨租户承诺从"单腿证据"（acme 零语料查空）升级为双向判别（各回各家 + 并发不共享 + 留痕可查）。
- 成本：Single-Flight 收敛粒度变细（跨租户不再互相合并——正确性优先于聚合率）；
  admin 面演示脚本/文档需 platform 凭证（seed 已调整）。
- 待办继承：多实例部署时 Single-Flight 若改 Redis Pub/Sub（ADR-0003 扩展点），组键必须
  原样携带三元组，绊线逻辑随载荷迁移。
