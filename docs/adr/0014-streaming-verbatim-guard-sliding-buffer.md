# 流式出口防幻觉：句级滑动缓冲窗口，用打字机观感换可拦截性

状态：accepted（2026-10-10，随「四个深度优化点」ROI 排序首项落地）

上下文：`VerbatimStreamFilter` 的机制在 [ADR-0010](0010-generation-layer-enforcement-split.md)
已立（按判据客观性分层设卡），但**流式场景下的工程冲突**没有独立成文。这个冲突是真实的、
有约束的、且被决策明确权衡过的：

1. **防幻觉核验天然是"拿到完整文本才能算"的判据**——VerbatimGuard 的核心是最长公共子串
   （LCS），token 级增量无从判断"这半个词是不是某段原文的开头"。要判连续重叠就必须拿到
   至少一个语义单元（句子）的完整边界。
2. **流式传输天然要求"拿到一个字就发一个字"**——TTFT（首字延迟）是 LLM 网关的核心指标，
   本项目实测 16ms（L1 回放）/ 46.3ms（端到端 p99）。等完整答案再发等于放弃流式，
   回到"转圈圈→整段文字一次性跳出"的旧交互。
3. **两件事直接冲突**：核验要"等完整"，流式要"立刻发"。

候选方案三条：
- **A 全文核验后一次性下发**：放弃流式，交互体验退回一次性输出。否决——本项目 SSE 面
  （`/api/v1/copilot/chat/stream`）与 OpenAI 兼容面（`/v1/chat/completions`）的核心价值
  就是流式；且"已渲染字符收不回"是 ADR-0010 否决纯事后检测的同一条理由。
- **B token 级增量核验**：每个 token 到达就跑一次 LCS。否决——判据不成立（半个词无从判
  重叠）且开销荒谬：n^2 DP × token 数，热点路径直接劣化。
- **C 句级滑动缓冲窗口**：token 攒到句末再下发，下发前用一小段"已吐尾部"做连续性检测。
  采纳——见下。

决策：**句级滑动缓冲窗口（Sentence-level Sliding Buffer）**，四个构件各有单一职责：

1. **句切分**：仅 `。！？；!?;` 与换行构成句末判据，英文 `.` 仅在跟随空白时算（保护
   `v1.2.3`、`Order-Service.java`、`192.168.0.1`）。理由：句是中文运维文本里"最小可判
   核验单元"，比 token 大（有边界）、比段落小（不用等太久）。
2. **缓冲 + 即时校验**：token 进 `pending`，凑满一句即调 `VerbatimGuard.longestOverlap`
   判定，通过即下发，超阈整句替换占位话术。TTFT 的实际口径 = **首个通过校验的句子的
   下发时刻**（ADR-0010 已立：数字变大是诚实化）。
3. **滑动 carry（已吐尾部 160 字参与下一句判定）**：防"表格式漏检"——模型逐行倒出原文，
   每行单独 ≤80 字不拦，拼接起来却是连续导出。160 必须 > 80（阈值），否则跨句连续体在
   句级切分处被"断开"，拼接漏检。截断后 carry 被占位符打断，逐字连续体外在地恒
   ≤80 + 一句的余量。
4. **安全冲刷（200 字无句读强制下发）**：模型偶发输出无句读长块时，再攒下去客户端整段
   黑屏。200 ≈ 一句正常长度上限，宁可放行（后续句仍带 carry 兜检测）也不憋死流。

后果：
- SSE delta 粒度从 token 变句，打字机观感变为"句式机"；面板回放本就句级分片（48 字
  chunk），观感一致（ADR-0010 已述，此处不重复）。
- **残留边界（诚实记账）**：若模型输出一段 >160 字的连续原文，且恰好每句边界与原文
  断点对齐，则每句的 carry 窗口内重叠都 ≤80，单句可过。缓解：句边界是模型自己的断句，
  与原文逐字对齐到这种程度在实测中未复现；真要堵需升格为"段级 + 累计已吐全文"核验，
  那会显著推高 TTFT——取舍指向软层的规则 5/6（ADR-0010）先行，本条不回退。
- ADR 计数 13 → 14；README 的 ADR 计数由 `offline/doc_numbers.py` 现算比对，改字是
  被门闩要求的，不靠人记得。
