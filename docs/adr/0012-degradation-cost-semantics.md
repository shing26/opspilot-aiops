# 降级代价语义：L1 同时降质量与降门控——接受而非修

状态：accepted（2026-09-24，新一轮迭代 grill 定稿，用户拍板"如实登记 + 同构锁"）

上下文：三级自适应降级状态机（见 CONTEXT「降级域」）自始把 L1 描述为"摘除向量路与 Rerank"。
2026-09-24 复核代码时查出两件事：

1. **一处宣称与实现分叉**：`CONTEXT.md` 与 `README.md` 曾把 L1 写成"纯 ES + 缩减 Prompt"，
   但 `ChatOrchestrator.runPipeline` 的 L1 分支只把检索模式切成 `es_only`，prompt 仍走同一个
   `PromptAssembler.build(query, chunks)`——"缩减 Prompt"从未实现，全仓 grep 只有那两处文档。
   已按"宣称必须真"当场撤除该措辞。
2. **一项从未登记的降级代价**：`HybridSearchService` 在 `noRerank`（含 L1 的 `es_only`）路径上把
   `topRelevance` 置为 `1.0`（注释自陈"best-effort 不做 rerank 门控"），而门控判据是
   `ChatOrchestrator` 的 `!fastPath && topRelevance < minRelevance`。两者相乘的后果是：
   **L1 期相关性门控实际失效，只剩"零召回才拒答"**。

第 2 点是有意的实现选择，但它的后果从未作为"降级代价"进入任何文档——文档只讲 L1 掉质量
（语义 Hit@1 88.2%→70.6%），没讲它同时掉了"不知道就不答"这条核心主张。

决策：**接受该降级代价，如实登记，不补阈值**。

1. 把 L1 的代价写全并落到文档：**质量降**（88.2%→70.6%，即 `es_only` 的既有实测值）+
   **门控降**（相关性级 → 零召回级）。落在 `CONTEXT.md` 降级域与 `README.md` 降级段。
2. 不引入 RRF 分数门控。
3. 把"L1 的检索侧等价于 `es_only` 模式"钉成回归锁（Java 单测 + 变异验证），防止未来有人
   给 L1 加回"缩减 Prompt"或别的分叉——分叉一旦出现，本 ADR 登记的代价口径立即失真。

否决项：

- **在 L1 用 RRF 分数做门控**：`min-relevance: 0.2` 是在 **Rerank 分数分布**上标定的，而 RRF 分数
  无量纲（`score(d) = Σ 1/(k + rank)`，只依赖排名）。照搬 0.2 会变成拍脑袋拒答，而未标定的阈值
  造成的**误拒是静默的**（用户只看到"拒答"，看不到"本可作答"）——比现状更糟。要真做，须先有
  一套 RRF 分数分布的标定实验，那是另一个立项。
- **在 L1 保留 Rerank**：那就不是降级了。Rerank 恰是过载时要摘掉的外部依赖腿（`gte-rerank-v2`），
  摘它正是 L1 的触发意义之一。
- **让门控降级保持静默**：现状缺陷的本质不是"门控失效"，而是"失效无人知道"。故本 ADR 的产物
  是登记，不是代码。

后果：

- L1 期"不知道就不答"弱化到零召回级。这是**过载时的已知取舍，不是缺陷**——但它必须在文档里
  说得出口，否则就是又一次"宣称与实现分叉"（本项目对这类漂移有前科，见 `README.md` 收纳规矩）。
- **重开触发线**（入 `OPS.md` §5 债务闹钟表）：出现一次"L1 期误拒或漏拒造成真实事故"且被
  真人/QA 复现 → 立项标定 RRF 分数分布并给出 L1 专用阈值。未触发不做。
- `L1 ≡ es_only`（检索入参与 prompt 组装两处均同构）由单测锁定；该断言同时是"降级路径与评测
  路径同构"的证据——L1 的质量数字因此可直接引用评测报告里 `es_only` 那一列，无需另测。
