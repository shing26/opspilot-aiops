# 复盘：客户端恒定 ~2.05s 死区，被误判为应用性能缺陷（51207_HOSTPORT_PROXY_LATENCY）

## 事故摘要

黑盒体验测评发现每个请求都慢约 2.05 秒，且**恒定**——不随负载变化。第一反应是应用性能问题
（首字节慢、模型慢、检索慢），排查一度指向 IPv6 解析。最终归因：Windows Docker Desktop
的**宿主端口代理固定开销**，属环境项，不是应用缺陷。真正的问题是测量点选错了。

## 时间线

- 客户端测到每次 ~2.05s，服务端审计 `took_ms` 只有个位数毫秒
- 用 127.0.0.1 直连重放，排除 IPv6/`localhost` 解析假说
- 改为宿主裸进程直跑：端到端 3-11ms；容器端口映射形态：仍 ~2.05s
- 结论：延迟由容器端口转发链路引入，与业务代码无关；性能口径改以服务端 `took_ms` 为准

## 根因分析

Windows 上 Docker Desktop 的端口映射要经宿主侧代理转发，单次请求引入约 2 秒量级的固定开销
（不同机器数值不同，但特征一致：**恒定偏移、不随负载增长**）。这类"恒定偏移"是环境项的指纹——
应用侧的性能缺陷通常随负载/数据量变化，而固定开销对所有请求一视同仁。
测量点错位则让这个信号被读成"应用慢"：客户端测的是"含环境链路的总时长"，
而服务端的 `took_ms` 才是代码的真实耗时。

## 修复措施

1. 口径修正：容器形态下性能读数**以服务端审计 `took_ms` 为准**，端上时间只作连通性参考
2. 需要真实端到端数字时（如演示录屏、SLA 断言），改用宿主裸进程或 host 网络模式
3. 在运维文档里登记为环境项，避免后续再次把它当缺陷排查（同一坑不重复付时间）

## 复盘教训

- **延迟数字必须标注测量点**：端上、反代、服务端三者可以差两三个数量级；
  不标测量点的性能结论等于没有结论
- 恒定偏移 ≈ 环境固定开销；随负载增长 ≈ 应用问题——用这条指纹先分型，再决定排查方向
- 环境项要写进文档：否则每个新接手的人都会再排查一遍同样的 2 秒
