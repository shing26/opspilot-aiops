# 复盘："备份成功"是假的：文件落在容器可写层，cron 每天假绿（51204_BACKUP_LAYER_MISSING）

## 事故摘要

账号库备份脚本连续多日报告成功，直到真要做一次恢复时才发觉：宿主 `backup/` 目录**什么都没有**。
备份文件确实被写出来了，但它落在容器的可写层里——容器一重建就随之蒸发。更危险的是
cron 只看调用是否报错，于是"备份链路完好"这个结论**连续多日无人质疑**，
直到灾难恢复的那一刻才暴露：账号库（系统里唯一不可再生的数据）实际处于零备份状态。

## 时间线

- 备份脚本改成走服务端 HTTP 接口（容器内执行写盘），调用返回成功，`backup/` 在容器里出现文件
- cron 每日执行，退出码 0，无告警
- 做恢复演练时在宿主机上找不到备份文件 → 反查发现文件只在容器可写层
- 确认 compose 未映射备份目录；顺带发现"备份成功"的判据只校验了 HTTP 状态

## 根因分析

存储路径与生命周期不匹配：备份路径锚定在**进程工作目录**（容器内 `/app/backup`），
而 compose 只映射了 `data/` 与 `logs/`，没映射 `backup/`。容器可写层随容器生命周期存在，
重建即清空——备份因此"每次都成功，每次都消失"。
第二层问题是**校验缺失**：成功判据是"调用没报错"，而不是"文件在预期的持久位置可读且非空"，
于是第一层问题被完全掩盖。写入侧与校验侧跨了容器/宿主这条边界，而校验没跨过去。

## 修复措施

1. compose 显式映射：`./backup:/app/backup`（备份落宿主卷，与账号库同生命周期）
2. 备份脚本增加**跨界校验**——服务端返回成功还不够，必须从宿主侧验证文件存在且非空：

```bash
test -s "backup/users-${DAY}.zip" || { echo "响应正常但宿主 backup/users-${DAY}.zip 缺失（容器未挂载 ./backup 卷？）"; exit 1; }
```

3. 校验失败即非零退出，让 cron 能报错（而不是继续假绿）

## 复盘教训

- **备份的成功判据必须是"能在目标位置读回来"**，绝不接受"写入调用返回成功"
- 任何跨边界（容器↔宿主、本地↔远端）的写操作，都要在**边界对侧**验证一次；只验一侧等于没验
- 长期绿的东西要抽查：无人质疑的"一切正常"是最高危的状态——本项靠一次恢复演练才戳破
- 唯一不可再生的数据（账号库）必须与它的备份在同一条生命周期里
