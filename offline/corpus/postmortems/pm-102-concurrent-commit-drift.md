# 复盘：交接文档过时与并行 session 的幽灵提交（51101_CONCURRENT_COMMIT_DRIFT）

## 事件概述

按 handoff 文档的待办队列施工前，`git log -S` 例行核查发现：文档标记"待修"的三项缺陷**已被另一个并行 session 修掉**（幽灵提交，本地历史里凭空出现，提交信息却引用着本 session 的产物）。若照单施工会撞已修代码、产出空转 diff；若直接跳过又会漏掉真缺口——那三项**修了但没配回归测试**。

## 根因

- 多 agent/多 session 并行推进同一仓库，文档生成时刻 ≠ 施工时刻
- 交接文档是快照不是活账本；"已修复"与"已锁定"是两回事——只有前者就是裸奔状态

## 处置

1. 每条待办开工前先验证存在性：`git log -S "<关键符号>"` + 读当前代码，不信任文档行号
2. 已修未锁的项转为**补回归锁**：对旧实现 `git checkout <fixed-point> -- file` 跑测试验证**能红**，再恢复——锁没有牙齿等于没锁
3. 报告中明确标注"文档第 X 部分已过时"，防止错误结论继续繁殖

## 防复发教训

- 并行环境下开工的第一动作是**rebase 事实**而不是 rebase 代码
- 修复类工作的完成定义 = 代码改动 + 能红能绿的回归锁，缺一不算闭环
- 外部 AI/他人给的建议同样要先对仓库取证再采纳——同一晚上，另一模型给的操作清单里三条有两处事实错误（不存在的文件、会自毁的"清理"建议）
