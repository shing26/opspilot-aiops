# 复盘：客户端自己的错却收到 5xx——错误分层按异常族漏网（51206_CLIENT_ERROR_LAYERING）

## 事故摘要

攻击参数面矩阵实测发现两类**纯客户端问题**被回成 500：
① 请求体 JSON 反序列化失败（字段类型错、截断 JSON、顶层数组）→ 500；
② `Accept` 与端点产出协商失败（OpenAI SDK 的**非流式默认请求头**即触发）→ 500。
后果不只是观感：客户端拿到 5xx 会认为"服务端故障"而重试，5xx 率虚高还会污染 SLO 与告警；
而问题本身客户端**本可自助修正**，却因状态码误导而无从下手。

## 时间线

- 第四轮 QA 已修过一批错误分层（全局异常处理器覆盖了常见参数校验）
- 本轮矩阵按"端点 × 异常族 × 变体"穷举攻击参数，发现两类落网
- 二者都在 mapping/反序列化阶段抛出，**不在已覆盖的异常种类清单里**，于是走了兜底 500
- 补分支后同一矩阵复跑：13 用例 × 5 端点，5xx 计数为 0

## 根因分析

错误分层按"异常种类"枚举，但同一族内有多个变体：
body 侧除字段校验外还有**反序列化失败**（`HttpMessageNotReadableException`）；
协商侧除"不支持的产出类型"外还有**入口 Accept 协商失败**（`HttpMediaTypeNotAcceptableException`）。
未枚举到的变体全部落进兜底分支 → 500。
深层原因：异常清单是**按已知案例**长的，而不是按"请求生命周期各阶段可能抛什么"推导的，
于是每修一次只堵一个变体。这是同一处的第二次漏网，也是最后被要求收敛为单一出口的原因。

## 修复措施

1. 按**请求生命周期阶段**补齐分支，而不是继续罗列案例：反序列化失败 → 400，
   Accept 协商失败 → 406，并各自留痕（`ev=invalid`，带 `path` 与原因）
2. 留痕与前一轮一致：客户端错不但要有正确状态码，还要在审计里可查（否则改错请求如坠迷雾）
3. 回归锁：攻击参数面矩阵（字段类型错 / 截断 JSON / 顶层数组 / 错误 Accept / 错误方法 ×
   `copilot/stream`、`/v1`、`search`、`auth/login`、`admin`），断言**每例都是 4xx 且 5xx 计数为 0**
4. 合法路径回归同批复验（检索命中、SSE 全链路 done），确认没有误伤

## 复盘教训

- 错误分层要按**生命周期阶段**穷举（解析 → 校验 → 协商 → 鉴权 → 业务），不能按历史案例累加；
  按案例长的清单永远比现实少一个变体
- **客户端错落 5xx 是双向伤害**：调用方误判为服务端故障并重试，运维侧被虚假 5xx 带偏
- 同类缺陷第二次出现就该收敛出口（统一异常映射），而不是再打一个补丁——本次即按此收口
