# 备份有效性排查手册（51204_BACKUP_LAYER_MISSING）

## 适用症状

- 备份脚本/cron 一直报成功，但目标目录里找不到文件，或容器重建后文件消失
- 恢复演练时才发现没有任何可用备份
- 备份体积异常小（0 字节或几百字节），或时间戳停在很久以前
- 迁移/重建容器后"备份历史"整体断档

## 排查步骤

### 第一步：确认文件到底写在哪里

1. 在**宿主侧**列目录：`ls -la backup/`；再进容器看：`docker exec <容器> ls -la /app/backup`
2. 两边不一致 → 该目录没有挂卷（写入落在容器可写层，随容器消失）
3. 查挂载：`docker inspect <容器> --format '{{json .Mounts}}'`，确认目标路径在挂载列表里

### 第二步：确认"成功"是什么口径

4. 查备份脚本的判据：只校验了 HTTP/退出码，还是也校验了文件存在且非空（`test -s`）
5. 只校验一侧 → 属于跨界未验证，直接判为**不可信备份**（哪怕文件此刻在）
6. 抽查备份内容：`unzip -l backup/users-*.zip` 或 `tar tzf`，确认里面确实有库文件而不是空壳

### 第三步：做一次真的恢复演练

7. 取最新备份解到临时目录，起一个临时实例指向它，确认账号/数据可读
8. 演练失败即为最高优先级修复项——**未演练过的备份按 0 备份处理**

## 止损操作

1. 立刻补全挂载再重跑备份：compose 增加 `./backup:/app/backup`，`docker compose up -d`
2. 在宿主侧验证产出：`test -s backup/users-$(date +%F).zip && unzip -l backup/users-$(date +%F).zip`
3. 把校验写进脚本并以非零退出码报错，恢复 cron 的报警能力
4. 立即做一次恢复演练并留档（比"再备份一次"更能证明链路可用）
5. 盘点同生命周期要求的其他目录（`data/`、`logs/`、审计打包）是否也在挂载列表里

## 升级路径

- 复盘"为何长期假绿"→ 审计所有 cron/定时任务的判据，凡"只看退出码"的一律补产物校验
- 需要异地/多副本 → 属备份策略变更，评估后另行立项（本手册只保证"单机备份真的存在且可读"）
