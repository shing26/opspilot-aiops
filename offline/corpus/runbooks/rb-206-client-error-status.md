# 客户端请求错误却回 5xx 排查手册（51206_CLIENT_ERROR_LAYERING）

## 适用症状

- 请求本身明显不合法（字段类型错、JSON 截断、`Accept` 头不匹配），响应却是 500
- 监控 5xx 率上升但服务端日志没有业务异常，只有 mapping/反序列化阶段的栈
- 调用方（尤其是第三方 SDK）陷入"重试 → 还是 5xx"的循环
- 某一个协议面（如 OpenAI 兼容面）比另一个更明显：SDK 的默认请求头就会触发协商失败

## 排查步骤

### 第一步：确认错误归属（客户端 vs 服务端）

1. 取响应体：本系统形态是 `{"code":"INVALID_REQUEST","message":"..."}`（协商失败为固定话术）
2. 用最小请求手工重放该端点，逐步加回原请求的头与体，定位是哪一项触发的
3. 看服务端日志的异常类型：`HttpMessageNotReadableException`（body 侧）、
   `HttpMediaTypeNotAcceptableException`（Accept 侧）、`MethodArgumentNotValidException`（校验侧）

### 第二步：按生命周期阶段核对覆盖

4. 列请求经过的阶段：**反序列化 → 参数校验 → 内容协商 → 鉴权 → 业务**
5. 逐个阶段问："这一阶段抛的异常有没有专属分支？"没有就会落兜底 500
6. 特别检查协商阶段：入口 `Accept` 与端点产出不匹配时，异常发生在进入方法之前

### 第三步：矩阵化复验（不要只修单例）

7. 组矩阵：端点 ×（字段类型错 / 截断 JSON / 顶层数组 / 错误 Accept / 错误方法）
8. 断言每一格都是 4xx **且网关 5xx 计数为 0**；同时跑一遍合法路径确认没有误伤
9. 把矩阵固化为回归锁（本系统为攻击参数面矩阵用例），改名或新增端点时同步扩格

## 止损操作

1. 补分支后立即复验矩阵，确认 5xx 归零；若仍有 5xx，继续按阶段找漏网族
2. 检查审计是否留痕（`ev=invalid` 带 path 与原因）：没有留痕就无法事后统计影响面
3. 清理监控口径：把修复前的虚假 5xx 从 SLO 统计里剔除，否则后续误告警不断
4. 通知调用方：状态码变了（500 → 400/406），依赖"按 5xx 自动重试"的客户端需同步调整

## 升级路径

- 同类缺陷**第二次**出现 → 不再打补丁，收敛为统一异常映射出口并补全族清单
- 第三方 SDK 因协商失败无法接入 → 评估该端点是否应放宽产出类型（并写 ADR 说明取舍）
